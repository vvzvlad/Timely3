## Критические

### C1. «Custom (strftime)» читает за границей массива

**Где:** `src/Timely.c:458`

Условие `(date_format>=195)||(date_format<=254)` тавтологично для `uint8_t` — любое
значение удовлетворяет хотя бы одной половине. Внешний `if (date_format < 195)`
(`Timely.c:417`) уже увёл локализованные форматы в `switch`, поэтому в `else` всегда
`>= 195`, и условие истинно всегда.

В `datestr[]` (`Timely.c:339-412`) ровно **60** элементов — индексы 0..59, форматы 195..254
(подсчитано). При `date_format == 255` вычисляется `datestr[255-195]` = `datestr[60]` —
чтение за концом массива. Массив **не** `static`: это локальный массив указателей,
материализуемый на стеке при каждом вызове, поэтому `[60]` читает соседний стековый слот,
и полученный мусорный указатель уходит в `strftime()` как строка формата.

255 — не теоретическое значение: `src/js/config.js:40` предлагает `['Custom (strftime)', 255]`
обычным пунктом выпадающего списка. `format_current_date()` вызывается из `update_slot_text()`
(комплекация «Date», дефолт для `slot_ctr_l`), то есть при каждой перерисовке даты.
Значение персистится (`Timely.c:2147`), поэтому эффект повторяется при каждом запуске;
восстановиться можно только сменив формат с телефона.

Побочно: ветка `else if (date_format==255)` — мёртвый код, а значит вся фича кастомного
формата даты не работает никогда, и значение, записанное в `custom_date_fmt`
(`Timely.c:1871`), не используется.

**Фикс:**

```c
// Test the sentinel FIRST, then a properly bounded range check.
// datestr[] covers 195..254 (60 entries); 255 means "use the custom format".
if (settings_get()->date_format == 255) {
  strftime(date_text, sizeof(date_text), adv_settings_get()->custom_date_fmt, currentTime);
} else if (settings_get()->date_format >= 195 && settings_get()->date_format <= 254) {
  strftime(date_text, sizeof(date_text), datestr[settings_get()->date_format - 195], currentTime);
} else {
  date_text[0] = '\0'; // never index the table blindly
}
```

Дополнительно: валидировать `date_format` при приёме (`Timely.c:1864`) и клампить после
`persist_read_data` (`Timely.c:2236`) — сейчас значение из flash принимается без проверки.

### C2. Миграция v11→v12 сама создаёт отравленное значение

**Где:** `src/Timely.c:2238`

```c
if (settings_get()->date_format > 234) { settings_get()->date_format = settings_get()->date_format + 1; }
```

`date_format` — `uint8_t`. При 254 миграция даёт 255, то есть ровно то значение, которое
стреляет в C1, причём у пользователя, который «Custom» никогда не выбирал. При 255
происходит заворот в 0 (молчаливый сброс на «MMMM DD, YYYY»). Миграция одноразовая
и необратимая.

**Фикс:** насыщать вместо заворота и не заходить на 255:

```c
if (settings_get()->date_format > 234 && settings_get()->date_format < 254) {
  settings_get()->date_format += 1;
}
```

### C3. Открытие страницы настроек уничтожает кастомные переводы

**Где:** `src/js/configpage.js:206`, `:209`

`langResolve('custom')` возвращает `BASELINE.language || "EN"` — выбор «Custom» нигде
не фиксируется, сохраняется предыдущий код языка. Дальше при следующем `showConfiguration`:
`renderField` выбирает в селекторе «English», `wireLang()` вызывает `onLang()`, и раз
значение не `"custom"`, вызывается `langFill("EN")`, которая перезаписывает **все** поля
переводов английской таблицей. Обработчик сохранения диффает против `BASELINE` (там лежат
пользовательские строки), видит расхождение и отправляет английские строки на часы.

Правки пользователя теряются безвозвратно **без единого его действия** — достаточно
открыть настройки. Тот же круг переписывает `language` на часах, а от него зависят
`set_unifont()` (`Timely.c:1342`) и вертикальные офсеты `apply_center()`/`apply_bottom()`.

**Фикс:** хранить сам факт выбора Custom, а не разрешать его обратно в код языка. Ввести
отдельный ключ `lang_mode` (только в localStorage, на часы не уезжает) либо записывать
литерал `"custom"`; в `renderField` выбирать пункт «Custom», когда стоит этот признак,
и в `onLang()` не вызывать `langFill()` в этом режиме.

### C4. Лимит длины payload не устранён — выбор языка снова теряет сохранение

**Где:** `src/js/configpage.js:251-256`

Коммит `1c2ecfe` ужал числовые настройки в позиционный массив (835 → 232 байта URL),
но строки переводов остались передаваться по имени, а это и есть объёмная часть.
Замер: дефолты — 148 байт JSON / 254 байта URL; переключение языка на Italiano —
1227 байт JSON / **1862 байта URL**, то есть в 2.2 раза больше того, что в 0.0.2
признали обрезаемым. Независимая оценка со стороны AppMessage: худший случай
(32 числовых + `strftime_format` + `language` + все 42 `trans_*` по объявленным `max`
двухбайтовыми символами) при 7 байтах накладных на тапл даёт ~1330 байт против
инбокса 1280, открытого в `Timely.c:2223` (`app_message_open(1280, 512)`, при том что
строкой выше закомментирован `app_message_inbox_size_maximum()`).

Ни ограничения длины, ни чанкинга, ни фолбэка нет. Пользователь выбирает Italiano →
Save → не применяется **ничего** (не только язык), и localStorage тоже не обновляется,
так что повтор даёт тот же результат.

**Фикс:** (а) открыть инбокс через `app_message_inbox_size_maximum()`; (б) в `configpage.js`
считать длину закодированного payload перед присваиванием `document.location` и при
превышении бюджета отказывать с видимым сообщением, а не молча; (в) как надёжное решение —
отправлять строки переводов отдельным AppMessage после подтверждения основного.

## Высокие

### H1. Возврат `strftime()` не проверяется

**Где:** `src/Timely.c:460-464`

`date_text` — 24 байта. `strftime()` при непомещающемся результате возвращает 0 и оставляет
содержимое **неопределённым** (без терминатора), а следующая строка делает
`snprintf(date_string, sizeof(date_string), "%s", date_text)` — чтение за пределами буфера
до случайного нуля. Кастомный формат допускает 31 символ (`config.js:95`), `%A, %d %B %Y`
даёт 28. Сейчас латентно только потому, что ветка 255 мертва — починка C1 делает это
немедленно достижимым, поэтому чинить надо одной правкой.

**Фикс:** проверять возврат обоих вызовов `strftime()` и при 0 писать `date_text[0] = '\0'`;
заодно увеличить буфер до 32+ байт.

### H2. Комплекация «Секунды» не тикает в двух рядах из трёх

**Где:** `src/Timely.c:1705-1709` и `src/Timely.c:1686-1698`

`need_second_tick_handler()` и `handle_second_tick()` проверяют только `show_week`,
`show_day`, `show_am_pm` — то есть ряд над календарём. Слоты статус-бара (`slot_stat_l/r`)
и центрального ряда (`slot_ctr_l/r`) не проверяются вообще. Выбрав «Секунды» в статус-баре
или в ряду над временем, пользователь получает значение, обновляющееся раз в минуту.
Два новых ряда добавили, а требование к тику не перевывели — прямое следствие того,
что определение комплекации размазано по пяти местам (см. A1).

**Фикс:** проверять все шесть слотов. Структурно — через таблицу комплекаций с флагом
`NEEDS_SECOND_TICK` (A1), тактически — расширить оба условия на `slot_stat_l/r`, `slot_ctr_l/r`.

### H3. Ошибка геолокации шлёт 998, часы понимают только 999

**Где:** `src/js/app.js:276`

`locationError` вызывает `sendWeather(998, ...)`. C-сторона распознаёт только 999:
`in_weather_handler` (`Timely.c:1755`) считает любое другое значение **успехом** и обнуляет
`weather_state()->requests` и `->failures`, а быстрый ретрай (`Timely.c:1661`) гейтится
на `current == 999`. То есть отказ геолокации — ровно тот сценарий, ради которого ретрай
писали, — навсегда его отключает и обнуляет счётчик отказов. Погода при этом рисуется как
«N/A» (`weather.c:24` считает всё ≥900 недоступным), но самовосстановления не происходит
до следующего планового тика. Тот же вызов не передаёт `city`, поэтому `city || ''`
(`app.js:97`) затирает последний известный город.

**Фикс:** слать 999; на пути ошибки не отправлять ключ `weather_city` вовсе, а не пустую строку.

### H4. Хендлы AppTimer не сбрасываются на ранних выходах

**Где:** `src/Timely.c:1076-1090` (и аналогично `request_timezone`, `battery_status_send`)

`weather_request = NULL` стоит только на успешном пути, а три `return` при неудаче
`app_message_outbox_begin()` / `dict_write_*` оставляют хендл указывающим на уже сработавший
таймер. `APP_MSG_BUSY` от `outbox_begin` — рутина при уже летящей отправке или нестабильной
связи. После этого перестают работать все гейтированные вызовы: ретрай по готовности JS
(`:1734`), ретрай «медленный Android-JS» (`:1663`), немедленное обновление при смене
единиц или интервала (`:2043`, `:2050`). Аналогично `timezone_request` гейтит единственный
запрос TZ при реконнекте (`:1291`), `battery_sending` — все будущие отчёты о заряде (`:1216`).
Диагностики нет: `my_out_fail_handler` пишет в лог только при включённой отладке.

**Фикс:** сбрасывать хендл в NULL **в начале** колбэка (таймер к этому моменту уже сработал),
а не в конце — тогда любой путь выхода оставляет гейт консистентным. Плюс защитить
безусловное `weather_request = app_timer_register(...)` в `:1660` от перезаписи живого таймера.

### H5. `localStorage` пишется до подтверждения доставки

**Где:** `src/js/app.js:344-356`

`localStorage.setItem("timely_settings", ...)` выполняется безусловно **до** того, как
`Pebble.sendAppMessage` подтвердил доставку; колбэк отказа только логирует, ретрая нет.
Числовые настройки это переживают (страница всегда шлёт все 32 ключа), а переводы — нет:
они дельта против `BASELINE`, а `BASELINE` берётся из этого же блоба (`configpage.js:184`).
После NACK телефон считает переводы применёнными, следующая дельта пуста, и часы навсегда
остаются со старыми строками.

**Фикс:** писать `timely_settings` только из success-колбэка `sendAppMessage`; при отказе
оставлять блоб нетронутым, чтобы дельта пересчиталась при следующем открытии.

### H6. Диагностика отказов доставки мертва — колбэк сам падает

**Где:** `src/js/app.js:149`, `:189`, `:354`

Все три колбэка отказа строят строку из `e.data.error.message`. PebbleKit JS передаёт
`e.data.transactionId` и `e.error.message`; `e.data.error` — `undefined`, поэтому колбэк
бросает TypeError и лог не печатается никогда. Единственная диагностика на пути, где
теряется сохранение настроек, не работает — в подсистеме, вся история которой состоит
из молчаливых потерь.

**Фикс:** `e.error && e.error.message`, и обернуть выражение так, чтобы иначе оформленное
событие не выбрасывало исключение из колбэка.

### H7. `decodeURIComponent` вынесен из `try/catch`

**Где:** `src/js/app.js:328-329`

```js
var decoded = raw.match(/^\{/) ? raw : decodeURIComponent(raw);   // вне try
```

Эвристика `^\{` покрывает только «телефон уже раскодировал». На обрезанном payload (C4)
строка оборвётся на неполном `%XX`, `decodeURIComponent` бросит `URI malformed` без catch,
и обработчик умрёт целиком. Двойное кодирование (`%257B`) тоже не обрабатывается.
Плюс все пути отказа немые: `:320` (`return`), `:331` (`catch { return; }`), `:344` —
ни одного `console.log`. Это прямая причина, почему баг сохранения прожил три релиза.

**Фикс:** внести строку в тот же `try`; в `catch` логировать первые ~80 символов `raw`;
добавить логи на все три пути отказа.

### H8. NaN/undefined в позиционном массиве убивает все 32 настройки

**Где:** `src/js/configpage.js:251`, `src/js/app.js:338-341`

```js
var n=[];for(var wi=0;wi<WK.length;wi++){var wv=o[WK[wi]];n.push(wv==null?0:wv);}
```

`Number("")` даёт `NaN`; `NaN == null` ложно, поэтому в массив попадает `NaN`, а
`JSON.stringify` превращает его в `null` → `sendAppMessage({..., show_stat_batt: null})`.
Достижимо тривиально: очистить поле «Low battery threshold (%)». Одна кривая ячейка
убивает сохранение всех 32 настроек разом.

Второй путь той же дыры: если ключ есть в `wirekeys.js`, но контрола на странице нет,
`wv == null` даёт `0`, и настройка пользователя молча обнуляется при каждом сохранении.

Третий: `app.js:339` итерируется по `WIRE_KEYS.length`, а не по `dict.n.length`. Короткий
массив (устаревшая страница, обрезанный payload) даёт `undefined` в хвостовых ключах;
длинный — все предыдущие значения уже разъехались по неверным ключам.

Значения не клампятся: `max=100` у number-инпута браузером при чтении из JS не принуждается,
999 уедет в `uint8` и завернётся в 231.

**Фикс:** в `configpage.js` — `var num = Number(wv); n.push(Number.isFinite(num) ? num : 0);`
плюс кламп по объявленным `min`/`max`. В `app.js` — отказ применять payload при
`dict.n.length !== WIRE_KEYS.length` с логом. Тест на round-trip (T4).

### H9. Два буфера переводов переполняются на кириллице

**Где:** `src/js/config.js:67-68` и `src/js/config.js:75`

- `trans_time_am` / `trans_time_pm`: `max: 6`, буфер `abbrTime[2][12]` (`locale.h:15`),
  копируется `sizeof-1` = 11 байт. Шесть кириллических символов («вечера») — 12 байт,
  обрезка приходится на середину UTF-8 последовательности.
- Полные названия месяцев: `max: 11`, буфер `monthsNames[12][21]` (`locale.h:6`),
  копируется 20 байт (`Timely.c:2119`). 11 кириллических символов — 22 байта, та же обрезка.

Результат — невалидный UTF-8 в персистентной таблице локали и битый глиф на экране.
Страница принимает значение без возражений, то есть показывает одно, а часы рисуют другое.

Остальные четыре группы проверены и имеют запас: `DaysOfWeek[7][34]` при `max: 12`,
`abbrDaysOfWeek[7][6]` при `max: 2`, `abbrMonthsNames[12][11]` при `max: 3`,
`statuses[2][26]` при `max: 9`.

**Фикс:** `max: 5` для AM/PM и `max: 10` для полных месяцев (расширять буферы нельзя —
это середина persist-структуры, см. M1). Заодно явно терминировать после каждого `strncpy`.

### H10. Русский язык недостижим из UI при полностью готовой поддержке в C

**Где:** `src/js/configpage.js:35-47`, `:206`

В `LANGS` только `EN` и `IT`; `LANG_OPTIONS` = Follow system / English / Italiano / Custom.
`langResolve('system')` для `navigator.language == 'ru'` даёт `LANGS['RU'] === undefined`
→ `"EN"`. `langResolve('custom')` возвращает предыдущий код (C3). То есть `language`
не может стать `"RU"` ни при каком сценарии.

При этом в C три RU-ветки: `set_unifont()` (`Timely.c:1342`) подключает юникодный DejaVu
с кириллицей — шрифт лежит в ресурсах с `characterRegex` на `Ѐ-Ѡ`, — и вертикальные
офсеты `apply_center()`/`apply_bottom()` (`Timely.c:711`, `:719`). Пользователь может вписать
русские месяцы через Custom, но увидит пустые глифы: кириллический шрифт не подключится.

**Фикс:** добавить `RU: langTable(...)` в `LANGS` и `['Русский', 'RU']` в `LANG_OPTIONS`.

### H11. Гейты качества не работают ни локально, ни в CI

Три независимых отказа, в сумме означающие, что строгие флаги облачной сборки
не проверяются **нигде**:

1. `tools/strict-check.sh:14` захардкожен на `${HOME}/.pebble-sdk/SDKs/current/...`,
   которого на машине нет — скрипт физически не может отработать.
2. `flake.nix:49` экспортирует `CFLAGS="-Wno-error"`, что снимает `-Werror` в dev-shell.
3. `.github/workflows/ci.yml` собирает только хостовые C-тесты (шесть чистых модулей)

### M5. Тип тапла не проверяется перед чтением `cstring`

**Где:** `src/Timely.c:1737-1752`, `:1871`, `:2083-2140`

Все обработчики разыменовывают `tuple->value->cstring` без проверки, что тапл
действительно `TUPLE_CSTRING` и что его длина покрывает копирование. Пришедший целочисленный
тапл даёт `cstring`, указывающий на 1-4 байта внутри буфера словаря, а
`strncpy(dst, src, sizeof(dst)-1)` читает до 23 (city), 31 (`custom_date_fmt`) или

`weather_lat`/`weather_lon`/`custom_date_fmt`. Достижимо от провайдера: `app.js:238`
делает `city = r.city || r.locality || ""` без приведения типа, так что ответ
`{"city": 12345}` уедет целочисленным таплом. Отладочные `app_log(..., "%s", ...)`
печатают буфер, у которого может не быть терминатора.

**Фикс:** хелпер `static const char *tuple_str(Tuple *t)`, возвращающий NULL, если
`t->type != TUPLE_CSTRING`, и форсирующий терминатор на `t->length - 1`; провести через
него все чтения и логи. В `app.js` — `String(r.city || r.locality || "")`.

### M10. Отрицательный час восхода печатается на час позже

**Где:** `src/Timely.c:560-566`

достижимо на высоких широтах, чей часовой пояс убегает вперёд солнечного времени.

**Фикс:** нормализовать `h` в диапазон [0, 24) до разбиения на часы и минуты.

## Тестовое покрытие и гейты

204 строки тестов на 5.5k строк кода. Хостовая сборка включает шесть чистых модулей;

но допуск нигде не зафиксирован. `my_floor(-2.5)` возвращает `-2.0` (усечение к нулю,
не floor) — безопасно лишь потому, что единственный вызывающий передаёт положительное

### Признано хорошим — не трогать
`layout.c`, `calendar.c`, `suntimes.c`, `timefmt.c`, `vibes.c` — маленькие, без зависимости

Однобайтовая версия persist с одной миграцией — адекватна; TLV и схемы версий были бы хуже.
